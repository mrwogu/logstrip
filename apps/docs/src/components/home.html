agents pay for every line.

A failing job prints hundreds of lines. Your agent reads all of them, and each token costs money and attention. Most lines are boot messages, health checks, passing tests and the same stack trace again. The few that explain the failure sit somewhere in the middle.

Cutting by hand means writing a new grep for every tool. Pasting it all means paying for the noise.

five stages, one pass.

LogStrip reads the log line by line and never holds all of it in memory. Each line goes through the same stages, so the same input gives the same output.

  1. classify. Samples the start of the stream. Prose, markdown, source and config pass through with secrets masked. Logs continue.
  2. sanitize. Masks tokens, keys and passwords. Replaces ids, timestamps and addresses with placeholders, so repeats can fold.
  3. score. Rates each line by level, keywords, stack frames and scanner findings. Keeps the context around a failure and drops the routine.
  4. dedupe. Folds repeats into [x3], hides internal library frames and refers back to blocks that already appeared.
  5. budget. With --max-tokens N, keeps the highest scoring lines that fit, in their original order.

not a model, on purpose.

Prompt compressors in the LLMLingua family run a language model to drop low-information tokens. That suits prose. A log needs whole lines, frames you can follow and the same answer every time.

This describes the approach in general. We have not benchmarked other tools, and we say where the answer depends.

LogStrip compared with model-based prompt compressors
Question model-based compressors logstrip
needs a model yes no
same input, same output depends on model, hardware and settings yes, pinned by snapshot tests
lines stay whole not guaranteed, tokens are removed inside lines yes: kept, folded or marked
repeats removed, no count [x412] and the values that differed
